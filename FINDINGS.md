# Dryv — Remaining Findings

Findings from the architectural analysis, excluding the three high-priority items already fixed.

---

## Medium Priority

### M1 — Replace `(dynamic)` dispatch with pattern-match `switch`
- **File:** `Dryv/Translation/JavaScriptTranslator.cs:152`
- **Issue:** `this.Visit((dynamic)expression, context2, negated)` uses DLR dynamic dispatch on every expression node during translation. This bypasses compile-time safety, allocates via the DLR call-site cache, and cannot be optimized by the JIT.
- **Fix:** Replace with a `switch` on the expression type, dispatching to the correct `Visit(...)` overload explicitly.

### M2 — Move static caches to instance-level on singletons
- **Files:**
  - `Dryv/DryvValidator.cs:17` — `static ConcurrentDictionary<Type, GroupedValidation> Cache`
  - `Dryv/RuleDetection/DryvRuleFinder.cs:30-31` — `static ConcurrentDictionary CompiledRuleCache` and `CompiledRuleTreeCache`
- **Issue:** Static caches live for the process lifetime, never invalidate, and leak state across unit tests. `DryvValidator` has no `ClearCache()` method at all.
- **Fix:** Move caches to instance-level fields on the singleton services (or inject an `IRuleCache` abstraction). Since these classes are registered as singletons, the caching lifetime is identical, but testability and invalidation improve.

### M3 — Split `DryvCompiledRule` into phase-specific types
- **File:** `Dryv/Rules/DryvCompiledRule.cs`
- **Issue:** This single class serves as rule definition, compiled rule, translated rule, and parameter definition. All properties are `internal set` and mutated across multiple pipeline phases, making the class hard to reason about.
- **Fix:** Split into separate types per phase (e.g. `DryvRuleDefinition` → `DryvCompiledRule` → `DryvTranslatedRule`). Each phase produces the next immutable type.

### M4 — Upgrade `LangVersion` to `latest`
- **Files:** `Dryv/Dryv.csproj:19`, `Dryv.AspNetCore/Dryv.AspNetCore.csproj:19`
- **Issue:** Both projects are pinned to C# 8 despite targeting up to `net10.0`. This prevents use of file-scoped namespaces, raw string literals, collection expressions, `required` properties, and improved pattern matching.
- **Fix:** Change `<LangVersion>8</LangVersion>` to `<LangVersion>latest</LangVersion>` in both csproj files. Modernise code incrementally.

### M5 — Resolve all TODOs and remove dead code
- **Locations:**
  - `Dryv/DryvTranslator.cs:73-76` — `// TODO: Update all that code.` — `arguments` array has index 0 wasted ("too cumbersome to update"). Wastes an allocation slot and is confusing.
  - `Dryv/Translation/TranslationCompiler.cs:93-94` — `// TODO: remove "$$MODELPATH$$"` — Dead placeholder still being `.Replace()`'d on every translation.
  - `Dryv/Translation/ExpressionInjectionHelper.cs:86` — `// TODO: can we delete nect block?` — Likely dead code around `Task` type checks.
  - `Dryv/RuleDetection/DryvRuleFinder.cs:318-323` — Empty `foreach` body iterating `RelatedProperties` but doing nothing.
  - `Dryv/Configuration/DryvServiceCollection.cs:26-30` — Commented-out type validation in `Add()`.
- **Fix:** Address each TODO individually: remove dead code, clean up the `arguments` array offset, delete the `$$MODELPATH$$` replacement.

## Low Priority

### L1 — Replace PowerShell code-gen with C# Source Generator
- **Files:** `Dryv/GenerateRuleMethods.ps1`, `Dryv/GenerateRuleParameters.ps1`, `Dryv/GenerateRuleServer.ps1` and their outputs `DryvRules`.g.cs` (~5,600 lines), `DryvRules`.server.g.cs` (~870 lines), `DryvRules`.parameters.g.cs` (~80 lines)
- **Issue:** ~6,500 lines of combinatorial overloads generated by PowerShell scripts, committed to the repo. Maintenance burden and easy to get out of sync.
- **Fix:** Replace with an `IIncrementalGenerator` C# Source Generator. Generated code stays in sync automatically, IDE support for navigation, no need to commit generated files.

### L2 — Deduplicate `GetElementTypeOrSelf`
- **Files:**
  - `Dryv/RuleDetection/DryvRuleFinder.cs:221-238`
  - `Dryv/RuleDetection/ModelTreeBuilder.cs:44-61`
- **Issue:** Identical method duplicated in two files.
- **Fix:** Extract to a shared utility in `Dryv.Extensions.TypeExtensions` (or `Dryv.Reflection.TypeExtensions`).

### L3 — Replace `Touple2` with standard types
- **File:** `Dryv/DryvClientValidationSet.cs:16-31`
- **Issue:** Custom `Touple2<T1,T2>` type with a misspelled name. Reinvents `KeyValuePair<T1,T2>`.
- **Fix:** Replace with `KeyValuePair<TKey, TValue>` or a dedicated named record. Check serialization compatibility.

### L4 — Re-enable type validation in `DryvServiceCollection.Add`
- **File:** `Dryv/Configuration/DryvServiceCollection.cs:24-35`
- **Issue:** The commented-out validation means any `Type` can be added to the Translators/Annotators collections. Failures surface only at runtime.
- **Fix:** Uncomment and update the type guard, or use separate generic-constrained methods.

### L5 — Add tests for AspNetCore and HotChocolate layers
- **Files:** `Dryv.AspNetCore.Tests/` (only 2 test files), `Dryv.HotChocolate/` (no tests)
- **Issue:** MVC filter, DI registration, client writer, middleware, and the entire HotChocolate integration are untested.
- **Fix:** Add unit/integration tests for `DryvValidationFilterAttribute`, `DryvConfigurationExtensions.RegisterDryv`, `DryvClientWriter`, and `DryvValidationTypeInterceptor`.

### L6 — Optimise `FindDisablingRules` string operations
- **File:** `Dryv/DryvValidator.cs:154-168`
- **Issue:** For every property being validated, splits `modelPath` by `.`, then reconstructs substrings with `string.Join` + `Take`. Excessive allocations on hot path.
- **Fix:** Build the lookup string incrementally with `StringBuilder` or use `ReadOnlySpan<char>` slicing.

### L7 — Duplicate DI registrations for `DryvOptions`
- **File:** `Dryv.AspNetCore/DryvMvcBuilderExtensions.cs:94-95`
- **Issue:** `DryvOptions` is registered both as `IOptions<DryvOptions>` and as the raw type. Two sources of truth.
- **Fix:** Pick one registration strategy. Prefer `IOptions<DryvOptions>` for consistency with ASP.NET Core conventions, or just the raw type if `IOptions` adds no value.

### L8 — Consider evaluating the custom 748-line `ExpressionVisitor<TState>`
- **File:** `Dryv/Translation/Visitors/ExpressionVisitor.cs` (748 lines)
- **Issue:** Custom expression visitor when `System.Linq.Expressions.ExpressionVisitor` exists in the BCL (available in `netstandard2.1+`). Maintenance cost.
- **Fix:** Evaluate whether this custom implementation still adds enough value. If the stateful visitation can be handled via closures or a context object on the standard visitor, consider migrating.

### L9 — Service provider abstraction via `Func<Type, object>`
- **Files:** Throughout `DryvValidator`, `DryvTranslator`, `DryvParametersHelper`, etc.
- **Issue:** Loses `IServiceProvider` features (scoping, `GetRequiredService`, keyed services). Error messages are generic.
- **Fix:** Accept `IServiceProvider` in the ASP.NET Core layer and keep `Func<Type, object>` only in the core lib. Or introduce a thin `IDryvServiceResolver` interface.
